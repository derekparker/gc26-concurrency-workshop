# Demo: The Racy Counter (presenter walkthrough, ~20 min)

Live-coded arc: a two-goroutine counter that loses updates → the race
detector explains why → three successively better fixes. The intermediate
steps are pre-baked as diffs so you can move fast. Step 0 puts you in
`01-race-detector/demo/`; **stay there and apply them by bare filename, in
this order**. Each diff builds on the previous one, so none of them are
skippable, including step 2.

| Step | Command (from `01-race-detector/demo/`) | Result |
|------|-----------------------------------------|--------|
| 0 | (none) | `counter.go` as committed: the racy version |
| 1 | `git apply mutex.diff` | coarse mutex: correct but serialized |
| 2 | `git apply trace.diff` | adds `runtime/trace` (also the bridge to section 02) |
| 3 | `git apply fix-mutex.diff` | fine-grained mutex inside the loop |
| 4 | `git apply atomic.diff` | `atomic.Int64`, no mutex at all |

Reset everything with `git checkout -- counter.go` (and `rm -f
counter.trace` if you generated one).

## Step 0, Show the bug (5 min)

Walk through `counter.go`: two goroutines, each increments a shared field
100,000 times. Point out `wg.Go` (added in Go 1.25), no more
`wg.Add(1)` / `defer wg.Done()` boilerplate to get wrong.

```bash
cd 01-race-detector/demo
go run .
```

Expected output, run it two or three times:

```
Final counter: 102120
Final counter: 104097
Final counter: 105006
```

Talking points:

- We asked for 200,000 and got roughly half. Where did ~95,000 increments go?
- `inc.counter++` is three operations: load, add, store. Two goroutines
  interleave them and one goroutine's store overwrites the other's.
- Ask the room: "is this a compiler bug? a scheduler bug?", it's *our* bug:
  a data race, and the program's behavior is undefined.

## Step 1, Run the detector, read the report (7 min)

```bash
go run -race .
```

You get two reports (a read/write pair and a write/write pair), both like:

```
==================
WARNING: DATA RACE
Read at 0x00c0000a4048 by goroutine 7:
  main.(*incrementor).increment()
      .../demo/counter.go:14 +0x3c
  main.(*incrementor).increment-fm()
      <autogenerated>:1 +0x18

Previous write at 0x00c0000a4048 by goroutine 8:
  main.(*incrementor).increment()
      .../demo/counter.go:14 +0x4c
  main.(*incrementor).increment-fm()
      <autogenerated>:1 +0x18

Goroutine 7 (running) created at:
  sync.(*WaitGroup).Go()
      /usr/local/go/src/sync/waitgroup.go:238 +0x6c

Goroutine 8 (running) created at:
  sync.(*WaitGroup).Go()
      /usr/local/go/src/sync/waitgroup.go:238 +0x6c
==================
...
Found 2 data race(s)
exit status 66
```

**Spend real time here, reading reports is the core skill.** Walk through:

1. Two stacks = the two conflicting accesses; same address (`0x00c...`),
   same line (`counter.go:14`), one of them a write. The
   `increment-fm() <autogenerated>:1` frame under each is the compiler's
   method-value thunk for `wg.Go(inc.increment)` — noise, but worth naming
   so nobody goes looking for it in the source.
2. "Previous write" = the earlier access the detector remembered.
3. "Goroutine created at" = where each party was launched. Note the catch:
   `wg.Go` starts the goroutine *inside* `sync`, so both goroutines report
   the same single frame (`waitgroup.go:238`) and you **can't** tell the two
   `wg.Go` calls apart. That's a real cost of the convenience, with a plain
   `go func() { ... }()` you'd get `main.main()` and the exact line. Frames in
   the runtime/stdlib are usually scaffolding; scan for *your* files.
4. Note the program *still ran* and printed a result, the detector reports
   and continues, then exits 66. Mention `GORACE="halt_on_error=1"`.
5. Mention cost: ~5–10× memory, 2–20× CPU, cheap in tests/CI, targeted use
   in production.

## Step 2, Fix #1: a mutex... in the wrong place (3 min)

```bash
git apply mutex.diff
go run -race .
```

```
Final counter: 200000
```

Correct! No race! Ship it? **Point out the flaw:** the lock is around the
*entire loop*, so goroutine 2 can't start until goroutine 1 has done all
100,000 increments. We fixed correctness by deleting the concurrency.

Ask the room: "how would you *prove* the two goroutines no longer overlap?"
You can't see scheduling in a race report, that's the execution tracer's
job (section 02). Apply `trace.diff` now:

```bash
git apply trace.diff
go run -race .    # same 200000; now also writes counter.trace
```

That writes `counter.trace`, which you'll open with `go tool trace` in the
next section to *show* the serialization. Don't skip this step even if
you're short on time, the remaining diffs build on it and `atomic.diff`
will not apply without it.

## Step 3, Fix #2: shrink the critical section (2 min)

```bash
git apply fix-mutex.diff
go run -race .    # still 200000, no race
```

Lock/unlock now wraps only the increment: goroutines genuinely interleave.
Talking point: lock granularity is a trade-off, finer = more parallelism,
more lock traffic; coarser = simpler, less parallel.

## Step 4, Fix #3: the right tool for a counter (3 min)

```bash
git apply atomic.diff
go run -race .    # 200000, no race
```

For a single machine word, `atomic.Int64` beats a mutex: no lock, no
blocking, and the type can't be accessed non-atomically by accident (unlike
the older `atomic.AddInt64(&x, 1)` free functions). Rule of thumb:
**atomics for a single independent word; a mutex the moment two pieces of
state must change together.**

## Wrap-up line

"The detector gave us the exact two lines and both goroutines in seconds.
Reports like this are also perfect AI-assistant input, it's evidence, not
vibes. Now you get three programs where the bug is much better hidden."

## Questions students actually ask

- **"Why was the counter *sometimes* right without `-race`?"** The race is
  still there; the schedule just didn't interleave destructively. Races are
  probabilistic, that's exactly why you need the detector.
- **"Does `-race` catch every race?"** No, only races that occur (unordered
  accesses) during that particular run, in code that actually executed. It
  never false-positives, though.
- **"Why not run `-race` in production always?"** Cost (see above). Do run
  it in CI, load tests, and canaries.
- **"Is `counter++` atomic on x86 anyway?"** No, it compiles to multiple
  instructions, and even single instructions don't give cross-goroutine
  ordering. The Go memory model, not the CPU, defines what's allowed.
- **"Could I use a channel instead?"** Yes, send increments to one owner
  goroutine. Idiomatic when there's real ownership to model; overkill for a
  counter.
